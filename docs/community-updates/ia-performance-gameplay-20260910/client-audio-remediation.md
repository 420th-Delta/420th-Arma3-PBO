# Baseline client sound-controller correction

SYS-08 was exposed after full integration admitted the graphical player. In `a599b201e269-integration`, the client recorded 18 native `Vehicle type expected!` warnings: the first immediately after player initialization at 21:02:44, followed by warnings at intervals of five to eight seconds. These warnings have no accompanying SQF exception or `ScriptError` event, so the ordinary script-error total alone does not establish a quiet client log.

`fn_initPlayerLocal.sqf` initializes `QS_client_soundControllers` using `getAllSoundControllers (vehicle player)`. `fn_clientCore.sqf` repeats the same vehicle query on `_QS_v2` every `5 + random 3` seconds. Bohemia explicitly states that [getAllSoundControllers does not work on humans](https://community.bistudio.com/wiki/getAllSoundControllers); [vehicle returns the unit itself when it is not mounted](https://community.bistudio.com/wiki/vehicle). The initial call and periodic cadence match the observed warnings. Both calls exist unchanged in pre-import commit `a99001f`, establishing this as an existing mission defect rather than part of the community contribution.

The two callsites now return an empty vehicle-controller array when their captured object is null or a human. Real vehicles still use the native query, and environmental controllers remain populated in the second array element. The only current consumer, `fn_clientDamageModifier.sqf`, reads that environmental element; this correction preserves its data shape and availability. No warning filter or native logging suppression is introduced.

Static validation checks the exact two production diffs, balanced SQF delimiters and the unchanged environmental expressions. The full-mission graphical retest below verifies on-foot initialization and repeated refreshes without this warning. Existing radio membership behavior is unaffected; replaying the entire focused radio fixture would not validate this sound-controller path. Native vehicle boarding/controller values and subsequent dismount remain distinct observations if the integration driver does not perform them.

Commit classification: keep this as a separate baseline fix, `fix(client): avoid vehicle sound queries while on foot`, containing the two production files; this explanation and the SYS-08 ledger entry belong to the final verification-documentation group. The inherited Forward Observer arsenal-role change already present in `fn_clientCore.sqf` belongs to the community support feature; only the sound-controller correction belongs to this follow-up commit.

Its graphical client initializes at 21:15:29, is admitted successfully, and records 25 heartbeat samples spanning **119.535 seconds** after admission. The entire final `client0.rpt` contains **zero** `Vehicle type expected!` warnings. This closes the focused on-foot initialization/refresh regression. This cell used the separately documented `reviewed-scout-v1` stock-MFD test control; it is not an unmodified-stock full-mission acceptance claim. Vehicle boarding/controller contents and dismount were not exercised by this driver.
