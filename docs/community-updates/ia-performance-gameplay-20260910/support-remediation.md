## SUP-1: lifecycle

The first dedicated/graphical fixture (`7249c16a2b31-support`) also exposed a separate inherited menu-call defect: all new support menu calls supplied Boolean `FALSE` as the fifth `BIS_fnc_addCommMenuItem` parameter. The native function emits `Type Bool, expected String` while reading its notification class. Both production functions now supply the empty string, which suppresses notifications as intended by [Bohemia's function contract](https://community.bistudio.com/wiki/BIS_fnc_addCommMenuItem). The fixture checks returned menu IDs and the runner rejects script errors; the original snapshot remains preserved as failing evidence.

The registered `postInit` mode maps to `INIT`. Initialization enters an unscheduled transition before checking/setting its existing once-only latch, so simultaneous scheduled initialization calls cannot duplicate the observer or event handlers. The two handler IDs and observer handle are retained in `localNamespace` for diagnostics. The normal two-second observer reconciles artillery and mortar menus, death/respawn, revive, role changes, and ping cleanup. Dedicated servers and HCs do not start this client observer.

Client control checks use `isRemoteControlling player`, including the dead-controlled-actor case where `remoteControlled` can become null. Server checks use the mission's replicated control flag and BIS owner markers, with a native query only for a local actor. These markers are integration signals, not an independent anti-cheat guarantee. The artillery worker checks them again during its delays; it does not retain a request-time control snapshot. Locality requirements follow the [Bohemia remote control tutorial](https://community.bistudio.com/wiki/Remote_Control_Tutorial).

The extended fixture exposed another locality assumption in artillery publication. A numeric-target `setVariable` only updates that target, so the server cannot use its own copy of the client status variable as a last-sent cache. That comparison could skip sending an empty status at activity end or role departure. Publication now stores `[owner,status]` in the server activity's `published` map keyed by body netId, and sends whenever that pair changes. Tests compare the expected server publication with the actual player's received status, including cleared states. This follows the [targeted setVariable contract](https://community.bistudio.com/wiki/setVariable).

## SUP-3: resource accounting

Each mortar reservation now records its request kind, admitted backpack object, whether the server initiated debit, and whether a placement acknowledgment was already accepted. All server modes run an unscheduled transition even when a custom client uses scheduled `remoteExec`. UID, body, owner, role, nonce, deadline, section cap and pending-request checks remain enforced.

The diagnostic run `0f65cd3133b8-support` identified the admission failure in the first correction: native `isNil` changed a scheduled remote call from `canSuspend=true, isRemoteExecuted=true, owner=4` to `false,false,0` in the recursive API entry. Role and tube checks remained valid. Both support functions now capture caller provenance directly from the engine before entering a lexical server closure under `isNil`; no request argument supplies those values. This preserves atomicity and authentication together. Artillery CANCEL now participates in that same atomic transition as request debit and watchdog refund, preventing scheduled cancellation from interleaving its refund with another transition.

For TUBE, a positive ACK is an intent to commit construction. The server verifies that the exact admitted backpack is still worn, then sends an authenticated DEBIT operation to its owner's machine. The receiver checks that same object again and removes it with the local `removeBackpack` command in one unscheduled operation. The existing server core waits for that captured backpack object to become null before issuing ammunition; no client success Boolean grants stock. Dropping or substituting a backpack leaves the captured object alive, and a delayed DEBIT targeting it cannot remove a replacement. A repeated ACK never performs another debit or adds another magazine. The local command follows [Bohemia's inventory contract](https://community.bistudio.com/wiki/removeBackpack).

The pending mortar contains no ammunition and is locked. This is necessary because the native carry helper may unhide an object before the server receives its ACK. Once paid, the server sends a single authenticated ARM operation to the turret's owner, which adds exactly eight HE rounds and unlocks the mortar. The free MORTAR request follows the same empty-then-arm path without consuming a backpack. After the second pass, its ten-minute cooldown starts only at successful server settlement and then survives RESET; a separate two-second attempt throttle applies before construction and also survives RESET.

The first algorithm used `removeBackpackGlobal` from the server. Independent review identified a timing window because that command targets the unit, whose backpack could change before the network effect arrives. The second native attempt (`300c69c24e6c-support`) demonstrated that dropping a backpack retains its container identity, but direct `deleteVehicle` probes failed both worn and dropped deletion assertions. That primitive was not adopted. The new DEBIT receiver closes the by-unit timing window by performing comparison and removal together where inventory is local; dedicated/client tests now cover a delayed DEBIT packet after a swap, including the replacement's contents and the original backpack on the ground. Final cell `b11ac9b1b0a4-support` proves ordinary ownership handoff and correct ARM delivery with different hull/turret owners. A forced turret-ownership change between accepted ACK and ARM delivery remains untested; the pending mortar is locked to prevent normal occupation from causing that change before settlement.

Run `429136a53def-support` passed actual DEBIT removal of a worn backpack and preservation of both the dropped original and replacement/FirstAidKit when DEBIT arrived after a swap. It also admitted exactly one of six concurrent scheduled requests with captured owner 4 preserved inside the unscheduled transition. A subsequent fixture defect prevented normal settlement polling: its test RPC attempted to invoke TICK within a remote context, which the production API correctly rejected. The fixture runs production TICK from its independent local server loop every 0.25 seconds during adversarial cases, then switches to the product's existing three-second core cadence for ordinary placement and section-cap cases. This historical run's wait failures are not a passing end-to-end accounting result.

Cancellation has an explicit boundary: a rejected, false, expired or reset request **before the server accepts its handoff** consumes no tube. An accepted handoff commits the tube cost; later reset/death/role departure retires that equipment without refund, as with a deployed mortar. If inventory deletion is not observed before the deadline, the mortar retires empty. No speculative refund creates another tube while a delayed removal remains possible. The protocol prevents this endpoint from minting mortars through a forged acknowledgment; it cannot make all Arma client-local inventory commands cheat-proof.

## SUP-10: deferred ownership handoff

The fixture attach dependency was never reached.

REQUEST now reserves its slot and exact backpack before returning. The existing core sweep retries ownership transfer only after the engine reports a nonzero owner and only while the connected body, role, nonce, readiness and deadline still match. No client packet can restart either window. There is no new per-request worker, and failed transfer retains the empty/locked state until retirement.

It also sends an ACK before handoff to verify that an admitted slot alone cannot debit a tube. All pass in `b11ac9b1b0a4-support`.
